1. Pipeline 的本体：一个 Buffer 的所有权交接

Pipeline 不是 copy engine，也不是 stage ring。它回答的是：哪些 warp 何时可以写、写完成如何被观察、哪些 warp 何时可以读、读完成如何允许下一轮覆盖。

producer_acquire等待 buffer 可写；producer 获得本轮所有权。
write(buffer)一个或多个 producer warp 按指令约束写 buffer。
producer_commit证明写已完成，或把异步完成事件连接到 full barrier。
consumer_wait等待数据 ready，并建立 consumer 访问需要的顺序与可见性。
read(buffer)一个或多个 consumer warp 读取；可能同步，也可能异步。
consumer_release同步读可立即释放；异步读把 completion 责任交给 pipeline，完成后 buffer 才再次可写。

固定语义

  • producer_commit 发布的是“本轮写入可被 consumer 安全使用”。
  • consumer_release 表示 consumer 交出本轮访问；同步 consumer 可立即发布 empty，异步 consumer 则提交可观察的 completion。
  • 同步的粒度是 logical buffer lifetime，而不是某条指令的名字。

由具体 Pipeline 决定

  • full / empty 是普通 mbarrier、transaction barrier、named barrier，还是专用 completion。
  • 谁 issue 指令、谁 arrive、arrival count 如何计算。
  • 是否要 wait、proxy fence、TCGEN05 fence、commit 或 multicast。
范围说明：这里把通信参与者抽象为 CTA 内的一组 producer warp/warpgroup 与一组 consumer warp/warpgroup。硬件指令仍可能要求 shared::cluster mbarrier 或 CTA-group 语义；那是具体 pipeline 的 completion/topology 细节。

2. 先归一化 Memory Effect，再谈指令名

两条指令只要对目标 buffer 具有相同的完成、可见性和参与者义务，就可以归入同一种 effect。反过来，即使都叫“load”或都访问 SMEM，只要这些义务不同，就不能共用 pipeline 端点语义。

Effect descriptor

struct MemoryEffectKind {
  Access       access;      // Read / Write / ReadWrite
  MemorySpace space;       // SMEM / TMEM
  Execution   execution;   // Sync / Async
  Proxy        proxy;       // Generic / Async / TCGEN05 domain
  IssuerSet    issuer;      // threads / warp / warpgroup / elected-one
  Completion   completion;  // scoreboard / mbarrier-tx / commit / wait...
};

为什么六个维度都需要

  • execution 决定 issue 后能否立即交接，还是必须等待异步完成。
  • proxy 决定跨访问路径是否需要 fence.proxy.async。
  • issuer 决定哪些线程发指令、哪些线程/完成域参与 arrive。
  • completion 决定普通 arrive、TMA transaction、bulk-group wait、TCGEN05 commit/wait 等具体路径。

4. 性能特化：只删除已经被证明冗余的同步

矩阵先决定不能违反的 buffer protocol family；随后 compiler 才能利用 same-role、锁步 stage schedule、单 issuer domain 等事实选择更小的完整实现。特化失败只能回退到同一格子的通用实现；若连通用协议要求的 transaction 对齐也无法证明，则编译报错。绝不能回退到另一个 effect family。

TmaStoreStream 不是第 11 种 Pipeline

TMA bulk group 属于 issuing thread/domain，而不属于某个 buffer。一组 store 可以同时读取多个 buffer，一次 wait 也可能 retire 多条 buffer edge。因此它应作为 issuer-domain scheduler 与多个独立 pipeline 协作，而不是塞进某个格子的通用状态机。

State 也按实现精确缩小

// two-role fallback
PipelineState<Stages> state_;

// one-cursor specialization
struct State { int stage; uint32_t phase; } state_;

两者都是 composition。one-cursor class 不应为了复用而携带死的 producer/consumer 双游标，也不应继承一个更大的 state base。

CTA-group / multicast 的位置：CtaGroup、静态 arrival count、transaction bytes 和 mask 是 topology facts，不增加 effect family。纯数值参数可以留作模板值；若 leader/peer remote-arrive、barrier ownership 或 storage 路径形成不同控制流，应拆为命名清楚的完整 specialization。
Proof rule：same-role 只是候选信号，不是证明。选择单 cursor 或删除 barrier 前，必须静态证明 transaction 对齐、producer-before-consumer、control-path cardinality、issuer domain、participant convergence 与 completion ownership。未知则选同 family fallback；transaction 不平衡则报错。
特化不是 endpoint policy：每个 specialization 仍是可逐行 review 的完整 struct，自己拥有 storage、state 和 transition 指令序列。Compiler 只做显式、保守的 class 选择；不需要一个通用 rule engine 或 Pipeline<ProducerPolicy, ConsumerPolicy>。

5. 一条指令可以连接多个 Pipeline

分析单位是“指令对某个 buffer 的 effect”，不是“指令属于哪一种 pipeline”。这对 UMMA、tcgen05.cp 和 TMA 尤其重要。

TMA load

对 GMEM 是 Read；对 staged SMEM 是 W.SMEM.TMA.Tx。CTA 内 pipeline 只关心后者。

TMA store

对 staged SMEM 是 R.SMEM.TMA.Bulk；对 GMEM 是 Write。SMEM 何时可复用取决于 source read completion。

tcgen05.cp

对输入 SMEM 是 R.SMEM.TCGEN05.Commit，对输出 TMEM 是 W.TMEM.TCGEN05.Commit。

UMMA

对 A/B-SMEM 是 async Read，对 D-TMEM 是 Write；accumulate 时 D 同时是 ReadWrite，TS 还会读 A-TMEM。

A/B SMEM writerGeneric 或 TMA write effect
→
input pipeline(s)按每个 SMEM buffer 选择 Generic→UMMA 或 TMA→UMMA
→
UMMA instruction消费 A/B；生产或累加 D-TMEM
→
output pipeline按 D 的后继 read effect 选择 UMMA→UMMA 或 UMMA→TmemLoad
Completion fan-out：同一条 TCGEN05 指令可能既需要释放输入 buffer，又需要发布输出 buffer。lowering 必须明确生成对应 mbarrier completion，并验证每个 tcgen05.commit 跟踪的 issue interval；不能让两个通用 endpoint policy 各自猜测同一批异步操作。

5.1 ll 与 ri：物理 Wrapper 与可分析复合指令

分层由公开语义和分析契约决定，不由 Python decorator 决定。ll_kernel(is_entry=False) 只是生成可复用 device function 的机制；它既不能自动把函数变成底层指令，也不能替代 memory-effect metadata。

Kernel schedulerole、stage.bind、遍历顺序、issuer predicate 与地址策略
→
ri semantic instruction稳定的复合数据变换 + logical memory operands + 可分析 effects/regions
→
ll physical wrapper单条 PTX，或因寄存器 tuple / inline-asm 约束必须捆绑的窄物理 macro

Kernel 保留什么

跨 fragment 的前后遍历、overlay-safe 顺序、runtime 分支、elected issuer、stage transaction 边界与 pipeline ownership。它们是 schedule，不应藏进方便函数。

ri 可以封装什么

一个可命名、可独立 lowering 的语义 transaction，例如固定宽度的 TMEM load → convert/activation → reduce/pack → TMEM/SMEM store。名字描述数据变换、空间和宽度，不描述某个模型或 kernel。

ll 可以封装什么

ISA 原语、bitcast/pack、barrier/fence wrapper，以及无法自然暴露寄存器 tuple 的窄物理 helper。ll 不拥有 logical buffer lifetime，也不替 compiler 决定 pipeline transition。

# Good: one analyzable semantic transaction. The name exposes datapath and repeat.
ri.tmem_ld_32dp_f32_to_smem_bf16_x8(
    accum_mem, output_mem, src_col, dst_addr)

# Declared metadata:
#   accum_mem: Read(TMEM), region(src_col, 32dp x8)
#   output_mem: Write(SMEM), conservative whole-buffer region when dst_addr
#               cannot yet be recovered as a logical SMEM view
# Lowering uses ll.tmem_ld_32dp, ll.tmem_ld_fence,
# ll.pack_bf16 and ll.st_shared_128.
Effect + region 是准入条件：每个 logical memory operand 都必须声明 access、space、proxy/completion，并让分析恢复 offset 与 extent。未知 region 可以保守地表示 whole-buffer access；需要精确 overlay、TMA partition 或局部复用证明时，不能靠 intrinsic 名字的 if/else 特判，也不能因封装而丢掉原本可见的范围。
内部 completion 与 pipeline transition 分开：复合指令可以内含使自身结果成立所必需的窄 ISA wait/fence，例如 TMEM load 后在使用寄存器前执行 tcgen05.wait::ld。但 producer_acquire/commit、consumer_wait/release、TMA-store stream commit/retire 等跨 logical buffer lifetime 的动作必须继续由 compiler 和 concrete pipeline 拥有。
先证明重复的是语义，不只是文本

至少两个 call sites 共享输入输出、memory effects、内部 completion 与 width；只有变量名或地址不同才值得抽取。

名字暴露可观察 layout

统一使用 ld/st；TMEM 指令显式写出 16dp/32dp 与 xN。不同 datapath/lane layout 使用独立 ri 指令，不能只用元素数掩盖。

边界停在一个 transaction

允许固定宽度 load/transform/store；不吞掉外层 tile loop、stage.bind、overlay traversal 或 issuer selection。

lowering 展开到 ll

ri 负责分析契约；物理 PTX/CUDA 实现放在 ll。若用 non-entry LLKernel，实现仍按其公开层级归类。

生成代码是验收标准

重构前后保存 CUDA/SASS；检查 helper 已内联、资源未恶化、effect/region events 等价，再批量迁移 call sites。

6. 实现原则：每个具体 Pipeline 都是独立 Class

统一的是 compiler-facing concept；不统一 barrier layout、completion hook 或 transition control flow。每个 effect family 至少有一个 class，证明成立时可增加窄 specialization。少量重复让每个实现可以被逐行 review。

基础 concept

template <class P>
concept WarpBufferPipeline = requires(P& p) {
  { p.producer_acquire() } -> std::same_as<void>;
  { p.producer_commit()  } -> std::same_as<void>;
  { p.consumer_wait()    } -> std::same_as<void>;
  { p.consumer_release() } -> std::same_as<void>;
};

四个名字固定插入位置和所有权语义，但不限制具体指令序列。对异步 consumer，consumer_release() 是“交出访问并提交 completion”，不保证函数返回时 stage 已物理可复用。

按需 capability

TmaLoadSource       // producer_prepare_transaction(), producer_get_barrier()
StagedPipeline      // producer_stage(), consumer_stage()
RetirableAsyncSink // retire_completed()
DrainablePipeline  // producer_tail()

只有真实 lowering 需要时才要求 capability；不要为“接口整齐”给所有 pipeline 填 no-op。

template <int Stages, int ProducerWarps, int ConsumerWarps>
struct PipelineGenericUmma {
  // Composition: the concrete pipeline owns its stage state.
  PipelineState<Stages> state_;
  BarrierArray<Stages> full;
  BarrierArray<Stages> empty;

  int  producer_stage() const { return state_.producer_stage(); }
  int  consumer_stage() const { return state_.consumer_stage(); }
  void producer_acquire(); // wait empty
  void producer_commit();  // proxy fence + full.arrive + advance
  void consumer_wait();    // wait full + required TCGEN05 ordering
  void consumer_release(); // tcgen05.commit -> empty + advance
};

允许共享

原始 PTX wrapper、barrier array view、elect-one、cluster rank/mask，以及只负责 index/phase 的 PipelineState 值类型。

不共享

Pipeline<ProducerPolicy, ConsumerPolicy>、通用 completion token、fence trait、由矩阵自动生成的 alias、带大量 no-op 分支的万能 storage。

禁止 state inheritance：具体类型写成 struct PipelineX { PipelineState<Stages> state_; ... };，不写 struct PipelineX : PipelineState<Stages>。Pipeline 不是一种 PipelineState；它只是拥有 stage cursor。composition 让状态访问、推进时机和额外的 inflight_ 等字段都留在具体实现中。
Collective 是协议的一部分：模板值可以描述 warp 数量或 CTA group，但“由所有 participant arrive”“由 elected lane issue”“由硬件 completion domain arrive”必须写在具体 class 中。若 topology 改变了控制流或 storage，就拆成另一个独立 class。

7. Stage 只是同一协议的多份 Buffer

Stage 解决吞吐，不定义同步种类。它用更多片上容量换取更多 in-flight work，使 producer 与 consumer 的执行重叠。

单份 Buffer 的协议不变

stage 0buffer[0]full[0] / empty[0] / phase
stage 1buffer[1]full[1] / empty[1] / phase
stage …buffer[…]相同 protocol state
stage N−1buffer[N−1]相同 protocol state

Little's Law 视角

required_inflight ≈ latency / initiation_interval

Stages 受以下因素共同约束：
  - 目标 overlap / issue interval
  - SMEM / TMEM 容量
  - barrier 与寄存器成本
  - occupancy
  - async engine queue depth

不进入 Effect Family

PipelineTmaUmma<1> 与 PipelineTmaUmma<4> 使用同一 completion / visibility 协议。

State 用 Composition

index、phase、wrap-around 可复用为 PipelineState，但它必须作为每个具体 pipeline 的成员，而不是基类。

容量仍影响局部逻辑

TMA store 的 pending-group 阈值可能依赖 Stages，但这只是该 class 的 queue capacity，不产生新 effect kind。

8. Compiler 如何自动选择 Pipeline

分析从 logical buffer 和 memory effect 出发。指令名只负责提供 effect metadata；先用矩阵选 family，再用显式的 proof predicate 选同一 family 内的具体 class。

collect + normalize为每个 buffer operand 记录 effect，并归一化 completion、proxy 与 issuer。
→
build buffer edges找出 write → read lifetime、participant sets、stage schedule 与 issuer domains。
→
matrix lookup按 write/read effect 精确选择 semantic family；无匹配则报错。
→
prove specialization显式证明窄条件后选小 class，否则使用该 family 的 fallback。
逐 operand 收集 effect

UMMA、tcgen05.cp、TMA 等一次产生多个不同 buffer effect；不能给整条 instruction 只挂一个 op kind。

构建 per-buffer producer / consumer regions

确定 first/last access、控制流覆盖、producer/consumer warp set，以及 buffer 是否真的跨 role 复用。

验证 region 内 effect 一致性

多个 opcode 可以归并为同一 normalized kind；若同一侧混入不同 completion 义务，拆 region 或编译报错。

精确查矩阵

family key 是 write effect × read effect；禁止按 memory space 相同退化到 generic mbarrier，也不要把 topology specialization 扩张成新的 effect kind。

保守选择 specialization

same-role 只是候选信号；还要证明 transaction 对齐、访问顺序、control-path cardinality、issuer domain 与 completion ownership。任何一项未知就选 fallback。

插入四个 transition

acquire 在首个 write 前；commit 在最后一个 write/completion issue 后；wait 在首个 read 前；release 在最后一个同步 read 或异步 read issue 后，把 completion 责任交给具体 pipeline。Stage reuse 仍必须晚于真实 completion。

最后 materialize stages

先确定协议种类，再按 stage count 复制 buffer/barrier state 并生成 cursor；stage 不参与 effect 分类。

for buffer in logical_buffers:
  edge = analyze_inter_warp_lifetime(buffer)
  if not edge:
    continue

  write_kind = normalize(edge.producer_effects)
  read_kind  = normalize(edge.consumer_effects)
  family = PIPELINE_MATRIX.lookup(write_kind, read_kind)

  if family is None:
    error("unsupported inter-warp buffer protocol", edge)

  pipe_class = family.fallback
  if family == TMA_TO_TMA_STORE and prove_one_cursor_relay(edge):
    pipe_class = PipelineTmaTmaStoreSameRole
  elif family == GENERIC_TO_TMA_STORE and prove_same_role_store(edge):
    pipe_class = PipelineTmaStoreSameRole

  insert_transitions(edge, pipe_class)
  materialize_stages(edge, pipe_class, edge.stage_count)
Less is more：这里只需要为真实存在的窄特化写两个显式 predicate；不要先造一个 specialization DSL、cost model 或规则引擎。新 predicate 只有在 benchmark 证明值得、且 correctness facts 可静态证明时再加入。

9. CUTLASS 对照：协议语义与 Stage State 分离

CUTLASS 的 pipeline 目录支持这套思路：公共调用面相似，但 TMA、UMMA、普通 barrier、TMA store 各有语义类型；stage index/phase 则由小型 PipelineState 表达。LittleKernel 选择把这个 state 作为每个具体 struct 的成员。
